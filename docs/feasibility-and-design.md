# 钉钉知识库治理服务：可行性与一期设计

**状态：** 设计完成，待最小权限 POC 验证

**服务标识：** `dingtalk_knowledge_governance`

**范围：** 钉钉知识库中文档的清单、时间线、增量与质量评审；不替代钉钉的知识库编辑体验。

## 1. 要解决的问题

管理者需要回答四个问题：

1. 每个知识库当前有多少份文件，按部门、文件类型和月份如何分布？
2. 历史文件何时进入知识库，谁创建、谁最后修改？
3. 本周期新增、变更、删除了什么；增量是否真实、可审计？
4. 新入库文档是否符合质量标准，评审分数和原因是什么？

这里的“入库时间”应拆为两个定义，避免统计歧义：

- `source_created_at`：钉钉节点的 `createTime`，代表该节点在知识库中创建的时间，是业务口径的“入库时间”。
- `discovered_at`：本服务首次采集到该节点的时间，是技术审计口径。历史数据首次接入时，两者通常不同。

## 2. 可行性结论

| 目标 | 可行性 | 实现方式 | 关键限制 |
| --- | --- | --- | --- |
| 获取知识库/文件数量 | 可行 | 分页递归读取目录树，按文件节点计数；保留每日快照 | 不能只统计顶层；必须遍历所有文件夹并处理分页 |
| 查询历史入库时间 | 可行 | 使用节点 `createTime`，同时保存 `creatorId`、路径与采集时间 | 表示知识库节点创建时间，不能等同于原文件在电脑上的创建时间 |
| 统计新增、修改、删除 | 可行 | 以稳定的 `nodeId` 对比相邻快照；用 `modifiedTime` 判断修改 | 删除要“二次确认”后再落库，防止权限或临时接口失败造成误报 |
| 获取钉钉原生评审分数 | 不可行 | 无 | 已核对本地钉钉 Wiki SDK 的节点数据模型，未发现质量/评审分数字段 |
| 生成本服务的评审分数 | 可行 | 元数据规则评分 + 正文 AI 评分 + 人工复核 | 仅靠节点元数据无法判断正文正确性、完整性或涉密风险 |
| 入库前阻断不合格文件 | 有条件可行 | 所有入库统一经过本服务的“提交—评审—写入”通道 | 若员工仍能从钉钉原生界面直接上传，服务只能事后发现，无法拦截 |

**推荐决策：** 一期先建设只读治理层和“入库后自动评审”，先把数据口径跑稳定；二期根据 POC 结果决定是否启用统一入库门户和写入权限，实现真正的质量门禁。

## 3. 已确认的钉钉数据能力

本地已存在的钉钉 `wiki_2_0` SDK 定义表明，节点列表/批量查询可取得：

- `nodeId`、`workspaceId`、`name`、`category`、`type`、`extension`、`url`
- `createTime`、`modifiedTime`、`creatorId`、`modifierId`
- `hasChildren`、`size`、可选的 `statisticalInfo.wordCount`

读取知识库与节点时，最低前置条件为：

- 应用凭据通过部署环境注入（不写入仓库）；
- 当前操作人可解析为钉钉 `unionId`，作为 `operatorId`；
- 应用开通 `Wiki.Workspace.Read` 与 `Wiki.Node.Read`，且该操作人拥有目标知识库访问权；
- 节点列表按钉钉分页限制读取，单页最多 30 条。

以下能力尚不能仅凭本地模型确认，必须在 POC 中逐项验证：文件正文下载/读取权限、节点变更事件是否可订阅、由应用创建节点所需权限、以及 API 限流配额。

## 4. 目标架构

```mermaid

    DT["钉钉知识库"] -->|"只读：库与节点元数据"| C["采集器"]
```

### 4.1 组件职责

| 组件 | 职责 | 一期是否需要 |
| --- | --- | --- |
| 钉钉连接器 | 获取并缓存应用 token；以登录用户 `unionId` 调用只读 Wiki API | 是 |
| 目录采集器 | 递归遍历工作区根节点，标准化节点元数据，生成同步批次 | 是 |
| 快照与审计库 | 存放当前节点、每日快照、同步结果、评分版本与评审记录 | 是 |
| 增量计算器 | 用 `nodeId`、`modifiedTime`、路径哈希计算新增/修改/移动/删除 | 是 |
| 评审引擎 | 规则校验、正文抽取、AI 评分、理由与人工复核 | 一期先做规则；正文 AI 评分需 POC |
| 管理 API / 看板 | 展示数量、趋势、入库时间线、增量清单、评分分布和待复核项 | 是 |
| 统一入库门户 | 上传、预检、评审、通过后写入钉钉 | 二期可选 |

## 5. 评审分数的设计

评审分数归属本服务，使用 **0–100 分、版本化评分标准**。2026-08-17 产品决策：拿不到正文不出分、不推送，只在任务日志记录原因；历史“元数据合规分”仅保留追溯。

| 维度 | 建议分值 | 一期数据来源 | 说明 |
| --- | ---: | --- | --- |
| 基础合规 | 25 | 名称、后缀、大小、目录、必填标签 | 命名、分类、文件类型是否合规 |
| 可用性 | 20 | 节点 URL、大小、字数、权限 | 排除空文件、异常小文件、不可访问文件 |
| 时效性 | 15 | `modifiedTime` | 按资料类别定义有效期，过期后扣分 |
| 内容完整性 | 20 | 正文抽取后 | 是否有摘要、适用范围、步骤、责任人、更新时间 |
| 内容质量/风险 | 20 | 正文 AI 评审 + 人工抽检 | 准确性、可执行性、重复性、敏感信息风险 |

评分记录至少保留：`node_id`、`score`、`score_version`、`dimension_scores`、`reasons`、`review_status`、`reviewed_at`、`content_fingerprint`。修改正文或评分规则版本变更时，必须重新评分，历史评分不覆盖。

建议状态机：`pending` → `auto_pass` / `needs_review` / `rejected` → `human_approved` / `human_rejected`。人工结论应带原因和操作者，形成可审计闭环。

## 6. 增量与历史口径

### 6.1 首次全量建基线

1. 读取可访问的知识库与根节点。
2. 对每个文件夹执行广度优先遍历，逐页读取全部子节点。
3. 仅把非文件夹节点计入“文件数”；文件夹数单独统计。
4. 写入首个 `sync_run`，为每个节点写入当前态和快照；历史“入库时间”从 `createTime` 回填。

### 6.2 后续同步的判定规则

| 结果 | 判定 | 展示口径 |
| --- | --- | --- |
| 新增 | 当前 `nodeId` 不在前一成功快照中 | 新入库文件数；按 `source_created_at` 和发现时间双列展示 |
| 修改 | `nodeId` 相同且 `modifiedTime` 或内容指纹变化 | 更新文件数；触发重新评审 |
| 移动/重命名 | `nodeId` 相同、路径或名称变化 | 不计新增，单列展示 |
| 删除 | 上次存在、本次全量成功扫描中不存在，且下一次仍不存在 | 删除文件数；先软删除保留证据 |
| 无变化 | 节点标识、版本和路径均未变化 | 不重复计入增量 |

“本月新增”应按 `source_created_at` 归属月份；“本服务本月发现”按 `discovered_at` 归属月份。两种报表不能混用。

## 7. 最小数据模型

| 表 | 关键字段 | 用途 |
| --- | --- | --- |
| `knowledge_workspaces` | `workspace_id`, `name`, `root_node_id`, `last_synced_at` | 知识库当前态 |
| `knowledge_nodes_current` | `node_id`, `workspace_id`, `parent_node_id`, `source_created_at`, `source_modified_at`, `path`, `is_file`, `is_deleted` | 文件/目录当前态 |
| `knowledge_node_snapshots` | `sync_run_id`, `node_id`, `source_modified_at`, `path_hash`, `metadata_hash` | 审计、增量计算与追溯 |
| `review_records` | `node_id`, `score`, `score_version`, `status`, `reasons`, `reviewed_at` | 质量评分历史 |
| `sync_runs` | `id`, `started_at`, `finished_at`, `status`, `scanned_count`, `error_summary` | 同步可靠性与可观测性 |

`creatorId`、`modifierId` 仅保存不可逆内部关联 ID 或映射后的员工主键；看板按最小必要原则显示姓名和部门，避免扩散个人信息。

## 8. 对外接口草案

```http
GET  /api/v1/knowledge-governance/overview?period=2026-08
GET  /api/v1/knowledge-governance/workspaces/{workspace_id}/files
GET  /api/v1/knowledge-governance/files/{node_id}/timeline
GET  /api/v1/knowledge-governance/files/{node_id}/reviews
POST /internal/knowledge-governance/sync-runs
POST /internal/knowledge-governance/reviews/{node_id}/recheck
```

后台接口必须鉴权；`operatorId` 从当前会话的钉钉身份映射得到，客户端不能自行传任意用户 ID。接口不返回 token、密钥或钉钉原始调试响应。

## 9. POC 验收与决策闸门

在一个非生产、可访问的测试知识库中完成以下验证后，再决定进入开发：

1. 配置不落盘地注入应用凭据，验证 `unionId`、`Wiki.Workspace.Read`、`Wiki.Node.Read`。
2. 在至少三层目录、含多页节点的测试库中全量扫描；抽样核对文件数、`createTime`、`modifiedTime`、创建人与钉钉界面一致。
3. 新增、修改、重命名、移动、删除各一份测试文档，连续运行两次同步，核对增量分类和删除二次确认。
4. 验证是否能以合规权限读取正文或下载文件；不能读取时跳过评审并记录原因。
5. 验证是否存在适用的节点变更事件；若不存在，采用低频定时全量扫描，并按实际限流数据设定频率。
6. 若目标是“先审后入库”，验证受控入口能否以最小写权限创建节点，并确认组织愿意关闭或约束绕开该入口的直接上传方式。

**进入一期开发的准入条件：** 前三项通过，并明确评分口径只覆盖已能合法取得的数据。

**进入二期门禁的准入条件：** 第四、六项通过，且业务明确统一入库流程和人工复核责任人。

## 10. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 将创建时间误当成原文件生成时间 | 在页面和报表中使用“知识库入库时间（节点创建时间）”全称 |
| 权限变化造成扫描结果缺失 | 每次同步记录操作者/权限错误；删除必须二次确认；告警不自动清除历史 |
| 仅依据文件名就给出内容质量结论 | 无正文时不评审、不推送，只记录失败原因 |
| LLM 评分不稳定或不可解释 | 评分规则版本化、保留维度和理由、高风险/低分项进入人工复核 |
| 知识内容或个人信息外泄 | 最小权限、内容最小化传输、脱敏、加密存储、访问审计；默认不保存正文 |
| 员工绕过质量门禁直接上传 | 把门禁定位为流程控制，不把轮询检测误称为阻断；需组织与权限配套 |

## 11. 推荐实施顺序

1. 完成 POC，冻结“文件”“入库时间”“增量”的统计口径。
2. 实现只读采集、快照、增量计算与总览看板。
3. 上线完整正文规则与人工复核；接入积分系统前先与业务确认“质量达标”的阈值和申诉规则。
4. 仅在正文访问、写入权限和流程约束得到确认后，建设正文 AI 评审及统一入库门禁。
