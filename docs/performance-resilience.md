# 页面性能、调用隔离与恢复方案

本文件是当前开发/部署参考。历史规划已归档，原始问题记录见 [工程 Review](reviews/2026-10-10-review.md)。实际测量与版本见 [发布验收](reviews/2026-10-10-release-validation.md)，不要将设计目标当成实测结果。

## 目标与边界

- 常用页面数据接口，热缓存、20 并发、40 请求/秒下 p95 ≤300ms，错误率为 0。包括真实会话验证；不以直接调用 Python 函数代替 HTTP 测量。
- 普通浏览、筛选、查询缓存刷新：钉钉 OpenAPI 新增调用为 0，不调用模型或 bi_center。授权登录仍需钉钉 OAuth，这与统计读取不同。
- 允许数据延迟 30 分钟：源数据聚合硬上限 10 分钟，加响应缓存硬上限 15 分钟；不额外用浏览器业务数据长缓存。两层最坏约 25 分钟，后台调度周期包含在各层硬上限内。
- 该时效针对**已经写入本地库的数据**。采集暂停期间不承诺钉钉到本地的 30 分钟延时，页面不因浏览而补扫描。启用采集必须另有额度评估及审批。
- 无法承诺所有故障永不发生；采用资源限额、失败隔离、可恢复备份和验收测试控制风险，不能以一次压测替代长期运行观察。

## 读取路径

`浏览器 → 认证/参数验证 → 进程内响应缓存 → MySQL 响应缓存 → 本地元数据聚合`

缓存仅覆盖 `app/read_cache.py` 白名单中的 GET。登录、密钥配置、人工写操作、导出鉴权、诊断外呼、实时钉钉接口不缓存。授权检查始终先执行，缓存不授予权限；响应使用 `private, no-store`。

| 层 | 刷新/限制 | 故障行为 |
| --- | --- | --- |
| 聚合缓存 | 5 分钟刷新，10 分钟硬过期；冷启动互斥 | 到硬上限必须重算，失败不续期 |
| 响应内存缓存 | 256 键、32MiB，总结果单项 ≤2MiB | LRU 淘汰，回退持久化响应 |
| MySQL 响应缓存 | 默认 10 分钟软刷新，15 分钟硬过期，约 512 键（并发插入可略超） | 软过期先返回旧值；硬过期重算或返回 503/Retry-After；新键淘汰最旧的非刷新条目 |
| 刷新调度 | 2 线程、最多 32 个待刷新键，数据库 120 秒租约 | 同键单飞，跨进程租约；主页面启动预热、活跃响应定时刷新 |

表 `read_cache_entries` 只保存现有元数据接口的 JSON 和时间戳，不保存正文或凭据；可丢弃重建，备份不包含此表。`X-KG-Cache`、`X-KG-Data-Age`、`X-KG-Generated-At` 可用于定位缓存命中与年龄。异常不能延长年龄。

页面不再在 GET 中解析/补查组织信息。组织信息由独立运维同步流程从 bi_center 更新；目标仍是使用对应月份快照，不在本服务复制七部门规则。原始 Review 的 R08 尚未完全解决：普通组织汇总仍有使用当前 EmployeeMap 的历史归属路径；不能将其作为准确的历史部门报表，后续需改为完整月度快照口径。

原始统计用记录数量作为变更戳，软删除和编辑可能不改变数量；现已改为有界周期重算。文档列表把分页放入 SQL，最新评分用窗口函数批量取回，避免分页越深 Python 内存越大及逐文档 N+1 查询。

文档库存源缓存保存基线独有节点 ID（最多 10,000 个）与总数，5 分钟软刷新、10 分钟硬过期。生产验证基线独有 129 个节点；新分页/筛选复用差异清单，避免反复对照十多万条基线记录。超限或快照变化时回退有界 SQL，不返回错误快照的清单。

## 交互与身份

- 登录独立页面，无菜单和业务图表加载；原业务 hash/部署前缀保留。网络、会话库或 OAuth 失败要明确可重试，不能假装已登录。
- 导航 abort 加每个局部区域自己的请求代次；筛选只接受最新响应。同一图表实例下钻时先解绑旧事件，避免多次触发。
- 会话 `last_seen_at` 最多每 5 分钟写一次，取消每次请求写库并再次读取已过期 ORM 的开销。会话撤销仍查数据库，不用长时间认证缓存。
- 治理配置和人工重评限定平台管理员；暂停评审返回 423，不允许“只入队、之后突然集中消费”。同文档并发手动点击复用活动任务，队列容量受限。
- worker 领取任务采用条件 UPDATE，只有成功领取者执行；启动恢复仅回收无租约的遗留任务和过期租约，不打断其他 worker 的活跃任务。评审仍维持暂停，启用前需核对队列与耗时上限。

## 运行限额与付费接口

Compose 默认仅 API。API 2 CPU/768MiB，worker 1 CPU/768MiB，watcher 0.5 CPU/384MiB；各进程最多 128 PID，日志 10MiB ×3；独立 `/tmp` tmpfs 128MiB。连接池 5+5、等待 3 秒，MySQL 连接 3 秒、读写 15 秒。线程/内存限额不是把共享数据库也当作无限资源。

PDF 提取隔离子进程，20 秒超时，Linux CPU 15 秒、地址空间 384MiB；损坏/超限文档跳过，不写正文。Office XML 解包也有展开大小上限。大文件仍需在 worker 被批准启用后持续观察。

`/api/health` 是进程存活；`/api/ready` 检查数据库并作为容器健康检查，不把数据库不可用标为业务健康。

实时钉钉目录代理增加 `KG_LIVE_BROWSE_ENABLED=false` 与管理员门禁。旧 `scan_uploader_baseline.py` 需要显式批准参数及全量开关，且改走共享额度适配器，不能再绕过计数。试验 probe/推送样例不进入运行镜像，源码仍保留供追溯；风险脚本使用前阅读 [脚本索引](../scripts/README.md)。

当前不引入 Redis：内存热缓存＋已有外部 MySQL 可满足目标，避免新增依赖。用户已允许未来采用 Redis；若多实例内存/缓存瓶颈被实测证实，再使用**数据服务器上的外部 Redis**，不在应用服务器部署数据库容器。Redis 只能缓存元数据，不替代持久化评审/任务，也不能绕过额度计数或认证。

## 验收与恢复

完整部署步骤、人员分工、密钥交接、回滚与重新启用规则见 [部署指引](deployment-guide.md)。

`scripts/ops_resilience.py` 仅访问本地 HTTP 和本服务 MySQL：

```sh
python scripts/ops_resilience.py snapshot
python scripts/ops_resilience.py benchmark --seconds 30 --rps 40 --concurrency 20
python scripts/ops_resilience.py backup --path /tmp/release.kgenc
python scripts/ops_resilience.py restore-drill --path /tmp/release.kgenc --key /tmp/release.key
```

- 压测自动生成十分钟有效的合成只读会话，结束撤销；不输出 Cookie、不进入人员统计，也不调用登录接口。默认仅允许容器 loopback，不接受任意公网压测目标。
- 备份流式、一致性事务读取，AES-256-GCM 分块认证加密；正文不在数据库里。备份与密钥权限 0600，立即复制到受控备份目录，密钥必须再分离存管，不能把二者一起发给外部部署人员。
- 加密备份保存除认证会话/查询缓存之外的本服务表。会话在恢复后重新登录；缓存重建。真正灾备恢复由 DBA 使用批准的版本、隔离实例先验收，再切换连接；本工具**不支持覆盖生产表**。
- 演练创建随机专属前缀临时表，对所有行逐列 SHA-256 校验、行数和外键孤儿检查；结束只删除本次临时表。遗留孤儿必须记录，不要在演练顺便删生产数据。
- 再分别测试 API 重启、响应缓存丢失后的重建、旧版本回滚、隔离环境数据库不可达/恢复。禁止停共享 MySQL。每一步记录耗时、计数、资源峰值和钉钉尝试计数差额。
- 部署指引中的定时备份/RPO、长期监控须由业务和 DBA 批准落实；本次请求不自动创建定时任务。
